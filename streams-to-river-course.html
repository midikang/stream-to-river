Module 1: What Stream to River Does

Your First Word Journey

Stream to River is an English learning app that helps you remember words using the Ebbinghaus Forgetting Curve.
When you click "Add Word", the app doesn't just save it. It creates a personalized review schedule that adapts to how well you remember each word.
Think of it like a smart garden: You plant seeds (words), and the app waters them (reviews) at exactly the right times. Words you struggle with get more water; words you know well get less.

// Clean up the word name
func cleanupWord(word string) string {
    word = strings.TrimSpace(word)            // Remove whitespace
    word = strings.ReplaceAll(word, "\n", "") // Remove newlines
    word = strings.ReplaceAll(word, "\r", "") // Remove carriage returns
    word = strings.ReplaceAll(word, " ", "")  // Remove spaces
    word = strings.ReplaceAll(word, "\t", "") // Remove tabs
    return word
}

Module 2: Meet the Cast

API Service, RPC Service & Frontend

Stream to River is built with three main actors, each with their own job. They communicate like a well-coordinated team.

The Three Actors

API

API Service

The gateway that talks to the outside world. Handles HTTP, validates requests.

RPC

RPC Service

The brain that does the heavy lifting. Generates quizzes, calculates review times, calls AI.

DB

Database

The memory that stores everything. Words, progress, user data.

Think of a library: The API Service is the front desk (taking requests), the RPC Service is the librarian (finding books and organizing), and the Database is the shelves (storing everything).

English

Why separate API Service and RPC Service instead of one big program?
It makes the code run faster
It allows them to scale independently and have different responsibilities
RPC is a newer technology that replaces HTTP
The database requires them to be separate

Module 4: The Memory System

Spaced Repetition & Quiz Generation

The magic of Stream to River is how it schedules reviews. It uses the Ebbinghaus Forgetting Curve to show you words right before you forget them.

The Ebbinghaus Forgetting Curve

━━━ Without reviews     ━━━ With spaced reviews

/rpcservice/global/keys.go Go 
const (
    LEVEL_0_INTERVAL = 5 * 60             // 5 minutes
    LEVEL_1_INTERVAL = 24 * 60 * 60       // 24 hours
    LEVEL_2_INTERVAL = 24 * 60 * 60       // 24 hours
    LEVEL_3_INTERVAL = 48 * 60 * 60       // 48 hours
    LEVEL_4_INTERVAL = 48 * 60 * 60       // 48 hours
    LEVEL_5_INTERVAL = 72 * 60 * 60       // 72 hours
    LEVEL_6_INTERVAL = 192 * 60 * 60      // 192 hours
    LEVEL_7_INTERVAL = 365 * 24 * 60 * 60 // 365 days
)

func GetReviewInterval(level int) int64 {
    switch level {
    case 0: return LEVEL_0_INTERVAL
    case 1: return LEVEL_1_INTERVAL
    // ... more levels
    }
}
Think of a video game: Each word starts at Level 0. Every time you answer all question types correctly, you "level up" and the next review gets scheduled further in the future.

Bitmask Scoring: The Secret Sauce

Each word has a score that tracks which question types you've mastered. It uses bitmasks - a clever way to store 4 booleans in one number.
0
CHOOSE_CN
1
CHOOSE_EN
1
PRONOUNCE
0
FILL_BLANK

Binary: 0110 = Decimal: 6

Code

// Set the bit for this question type reciteRecord.Score |= (1 << (questionType - 1)) // Check if all bits are set (MAX_SCORE = 15 = 1111) if (reciteRecord.Score & maxScore) == maxScore { // All question types mastered! reciteRecord.Score = 0 reciteRecord.Level++ interval := global.GetReviewInterval(reciteRecord.Level) reciteRecord.NextReviewTime = now.Add(interval).Unix() }

English

When you answer correctly: We "turn on" the bit for that question type using bitwise OR.

When all 4 bits are on: Score becomes 15 (binary 1111). You leveled up!

Reset and schedule: Score goes back to 0, level increases, and we calculate when you should see this word again.

Your score for "ubiquitous" is 13 (binary 1101). Which question type have you NOT mastered yet?
CHOOSE_CN (bit 0)
CHOOSE_EN (bit 1)
PRONOUNCE_CHOOSE (bit 2)
FILL_IN_BLANK (bit 3)

Module 5: AI Superpowers

Chat, Speech & Vision

Stream to River integrates three AI capabilities: LLM chat, speech recognition, and image-to-text.
The chat feature is the most complex. It streams responses in real-time using SSE and runs multiple goroutines in parallel.
Think of a conductor with an orchestra: The chat handler is the conductor. It starts three musicians (goroutines) playing simultaneously: one generates AI text, one highlights words, and one reviews for safety. They all play together in harmony.

Parallel Goroutine Orchestra

/rpcservice/biz/chat/chat.go Go 
func ChatHandler(ctx context.Context, req *words.ChatReq, stream words.WordService_ChatServer) error {
    // Create channels for communication
    reviewEnd := make(chan bool, 1)
    highlightResourceChan := make(chan string, 100)
    highlightResultChan := make(chan []HighlightItem, 100)

    // Goroutine 1: Review the prompt for safety
    gopool.CtxGo(ctx, func() {
        reviewEnd <- PromptReview(ctx, req.QueryMsg)
    })

    // Goroutine 2: Highlight words in the response
    gopool.CtxGo(ctx, func() {
        cozeHighlight(ctx, highlightResourceChan, highlightResultChan)
    })

    // Goroutine 3: Send highlight results to client
    gopool.CtxGo(ctx, func() {
        for highlightItems := range highlightResultChan {
            stream.Send(ctx, &words.ChatResp{
                Extra: map[string]string{"meta_info": metaInfo}
            })
        }
    })

    // Main goroutine: Stream AI response
    for {
        chunk, err := modelMsg.Recv()
        if err == io.EOF { break }

        respFullText += chunk.Content
        stream.Send(ctx, &words.ChatResp{Msg: chunk.Content})
        highlightResourceChan <- chunk.Content
    }
}

Code

var modelMsgSendDone int32 = 0 defer func() { atomic.StoreInt32(&modelMsgSendDone, 1) }() errSend := stream.Send(...) if errSend != nil && atomic.LoadInt32(&modelMsgSendDone) != 1 { klog.CtxErrorf(ctx, "send failed") }

English

We use an atomic variable as a flag.

When the main function exits, we set the flag to 1.

Other goroutines check this flag before logging errors - if the main goroutine already exited, the error is expected.

Goroutine Timeline

Main Thread:
Stream AI chunks →
Goroutine 1:

Goroutine 2:

Goroutine 3:

All running simultaneously, communicating via channels

Why does the chat handler wait up to 2 seconds for highlights to finish, but only 300ms for prompt review?
Highlighting is more important than safety
Prompt review is fast (p99 = 300ms), but highlighting processes the entire response which takes longer
The numbers are arbitrary and could be anything
Highlighting uses a slower external API

Key Takeaways for AI Development

1. Separation of Concerns

API Service handles HTTP, RPC Service handles logic. This makes the codebase easier to navigate and scale.

When prompting AI: "The API layer should only validate and forward requests to RPC"

2. Concurrency Patterns

Use goroutines + channels for parallel work. Atomic variables prevent race conditions.

When prompting AI: "Run the review check in a goroutine and communicate via a channel"

3. Bitmasks for Efficient State

Store multiple booleans in a single integer using bitwise operations.

When prompting AI: "Use a bitmask to track which question types the user has mastered"

4. Streaming for Real-Time UX

Use SSE to stream AI responses chunk by chunk instead of waiting for the complete response.

When prompting AI: "Stream the LLM response using Server-Sent Events"

Final metaphor: This codebase is like a well-run kitchen. The API Service is the waiter (takes orders, serves food). The RPC Service is the chef (prepares complex dishes). The Database is the pantry (stores ingredients). And the AI services are the specialized tools (like a pasta maker or ice cream machine).
